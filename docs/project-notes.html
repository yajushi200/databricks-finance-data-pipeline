Note 01 — Project Skeleton & the Databricks CLI · July 2026

1. What we're building (30-second recap)

A fraud-detection data pipeline on Databricks Free Edition using the medallion architecture: raw transaction data lands in bronze, gets cleaned and validated into silver, and is aggregated into gold tables that feed an ML fraud model. Everything is stored as Delta tables, versioned in GitHub, and deployed with Databricks Asset Bundles.

2. The project skeleton — what each file is and why it exists

The core idea: treat the pipeline like a real software project from day one, not a pile of notebooks. Code lives in git, logic is testable, deployment is repeatable, and nothing is clicked together by hand in the Databricks UI. This is exactly what employers mean by "data engineering best practices."

Note 02 — Learning Roadmap · July 2026

Guiding principles

1. Data model first, ML last. Bronze → silver → gold is the real project; the fraud model is the payoff chapter that proves the pipeline delivers something usable.

2. Medium data to build, big data to optimize. Start on ~1M rows so mistakes cost seconds; scale up only when it's time to feel (and fix) slow queries.

3. One new concept per phase. Formats, streaming, and optimization arrive one at a time — never overwhelming, always compounding.

4. Every phase ends the same way: commit + push, CI green, note appended to this file.

Dataset decision

PaySim (Kaggle) — ~6.3M simulated mobile-money transactions modeled on real financial logs. Chosen because its columns are human-readable (type, amount, sender, receiver, balances), it carries real fraud labels for the ML phase, and its step column (1 step = 1 hour of simulated time) lets us split one static file into hourly/daily arrivals — real data, but arriving like production data would.

Rejected alternatives: IEEE-CIS and ULB Credit Card (PCA-anonymized columns — can't practice data modeling on meaningless features); Bank Account Fraud NeurIPS (restrictive license).

The five phases

Phase 1 — Base data model (batch · CSV · ~1M rows)

Slice PaySim into daily CSV batches in a landing volume. Build the full medallion: bronze ingestion, silver cleaning transforms as tested Python functions in src/, quality expectations with quarantine (bad rows kept, not dropped), gold aggregates.

Ingestion is learned by hand first — a ladder where each rung solves the previous rung's problem:

RungMethodThe lesson
1Plain spark.read + appendRun it twice → duplicates. Ingestion has no memory of what's been processed.
2Hand-rolled incrementalFix it yourself: a log table tracking processed files, ingest only new ones, MERGE for idempotent writes. This is the core logic Auto Loader automates — checkpointing, exactly-once, dedup — built by hand.
3COPY INTODatabricks' built-in SQL command that does the file tracking for you. Recognizable, because you just built it.
4Auto Loader (deferred to Phase 3)Adds schema evolution and scales to millions of files. Not magic by then — just a better version of your rung-2 code.

You learn: Delta tables, medallion architecture, Unity Catalog volumes, idempotent ingestion logic, Lakeflow expectations, the edit → deploy → run loop.

Phase 2 — File formats (JSON + Parquet join CSV)

Pretend three source systems deliver differently: one sends CSV, one JSON, one Parquet. Convert further PaySim slices and extend bronze to ingest all three into the same tables. Pipeline logic barely changes — that's the lesson.

You learn: schema handling per format, schema evolution, why Parquet is the columnar favorite.

Phase 3 — Streaming (Auto Loader + AvailableNow)

Same tables, new arrival mode. A drip-feed script drops files continuously; Auto Loader (rung 4 of the ingestion ladder) picks them up incrementally with exactly-once guarantees. A file-arrival trigger fires the job automatically when data lands.

You learn: Structured Streaming, checkpoints, triggers, Auto Loader — and that batch vs streaming is almost the same code in Databricks.

Phase 4 — Scale & optimization (full 6.3M rows +)

Load everything (and synthetically multiply if needed). Measure slow queries, then fix them: liquid clustering / partitioning, OPTIMIZE, incremental MERGE instead of full rewrites.

You learn: Delta performance tuning, file compaction, incremental upserts — with data big enough to feel the difference.

Phase 5 — ML & automation (MLflow fraud model)

Train the fraud model on gold-layer features, track experiments with MLflow, and automate data-quality monitoring. The smallest phase — the gold features are what made it possible.

You learn: MLflow tracking, feature engineering from gold tables, quality automation.

Note 03 — Knowing the Data: Source Interview & Bronze Design · July 2026

The dataset, in plain words

PaySim simulates a mobile money service (like M-Pesa or a Paytm wallet): your phone number is your wallet. 6.36M rows over 31 simulated days; one row = one money movement. The five types: CASH_IN (deposit), CASH_OUT (withdraw), PAYMENT (pay a merchant), TRANSFER (send to a customer), DEBIT (send to a bank).

The step column is the only timestamp: hours since simulation start (1–744). step=50 = day 3, ~2am. Day = (step-1)//24 + 1. No minutes, no seconds — a real limitation of this source.

The fraud pattern (why single rows can't reveal it)

A fraudster hijacks an account, transfers the entire balance (amount = old balance, new balance = 0.0) to a mule account, which cashes out within the hour. Each transaction alone looks innocent — millions of people do transfer → cash-out daily. The fraud is only visible in context: amount vs balance ratio, paired transactions, speed. That context is what the gold layer exists to compute. The bank's old rule (isFlaggedFraud, flags only transfers > 200k) catches almost nothing — which is why this project exists.

Key concept learned: grain

Grain = what one row represents. Declaring "row = customer" then listing transaction-level fields (amount, balance before/after) mixes grains — the classic data modeling mistake. At customer grain, every field must be an aggregation: counts, sums, maxes, ratios ("max % of balance moved in one transaction today"). Rule of thumb: design backwards (gold's grain comes from the consumer's questions), build forwards (bronze → silver → gold).

Note 04 — Notebook Structure & the %run Path Error · July 2026

The decision: one place for configuration

The idea: the landing volume path is a value that will change — a different catalog, a different workspace, an eventual Azure deployment. Written into every notebook, that change becomes a search-and-replace across the project. Written once in a helper notebook, it becomes a one-line edit.

Notebooks in the Databricks workspace were therefore organised into folders rather than left flat:

Project-financial-pipeline/
├── 00_helpers/
│   └── config                    ← landing volume path, catalog/schema names
└── 01_bronze/
    └── 01_ingest_transactions    ← consumes config via %run

The bronze ingest notebook pulls the shared values in with %run, which executes another notebook in the current notebook's session — so any variable defined in config is available afterwards, exactly as if it had been typed at the top of the cell.

The error

The first attempt failed before a single line of Spark ran:

%run ../00. helpers/01.environment-config
Failed to parse %run command: string matching regex '\$[\w_]+' expected
but 'h' found. If notebook path or value contains spaces, wrap with
double quotes.

Root cause

The folder was named 00. helpers — with a space after the dot. %run is a magic command, not Python: it parses its argument as a single bare token and treats whitespace as the end of that token. Parsing stopped at the space, and the remaining helpers/... was read as an unexpected second argument — hence the complaint about the character 'h'.

Two fixes, and why only one of them counts

FixVerdict
%run "../00. helpers/01.environment-config"
(wrap the path in quotes)		Band-aid. Works, but fixes exactly one call site and leaves the underlying naming problem in place.
Rename folders and notebooks to remove spaces, dots and hyphensAdopted. Removes the whole class of failure, not this one instance.

Why renaming was worth the churn

CharacterWhat it breaks
SpaceResurfaces in Asset Bundle YAML, Databricks CLI arguments, job task definitions, and git on Windows. Quoting solves it once; renaming solves it everywhere.
DotBlocks any future import. Shared code consumed today via %run is better imported as a Python module once the project moves to Asset Bundles — and Python reads a dot as a package separator, so 01.environment-config could never be imported.
HyphenInvalid in Python identifiers, for the same reason.
Leading digits (kept)Harmless in folder names and they preserve execution order when the workspace lists folders alphabetically — 00_helpers before 01_bronze.

Convention adopted: underscores only. No spaces, no dots except genuine file extensions, no hyphens.

Design note carried forward

The config notebook currently hardcodes /Volumes/workspace/bronze/landing/. That literal will not survive deployment to an Azure Databricks workspace, where the catalog and volume differ.

The eventual fix is to supply it as an Asset Bundle variable resolved per target, so dev and azure bind different values without editing a single notebook. Not built yet — the discipline for now is simply that the literal path appears in 00_helpers/config and nowhere else, which keeps that swap cheap when it comes.

You learn: %run as Databricks' notebook-composition mechanism, magic commands vs Python syntax, and why naming hygiene is an engineering decision rather than a cosmetic one.

Note 05 — First Read: Everything Is a String · July 2026

What we did

Read the day-1 landing file with the plainest possible Spark read — no schema, no options beyond header — specifically in order to watch it fail. The bronze contract already says "explicit schema at read, never inferSchema." This note is the evidence behind that rule, gathered first-hand rather than taken on trust.

df = (
    spark.read
    .format("csv")
    .option("header", "true")
    .load(source_file)
)

Two bugs on the way in, both worth recording:

1. spark.read() → spark.read. read is a property returning a DataFrameReader, not a method. Adding parentheses tries to call the reader object itself.

2. Double slash in the path. landing_folder_path ended with / and the f-string added another, producing …/date=2026-06-01//transactions.csv. Spark tolerates it, but the value lands verbatim in the source_file audit column later. Convention fixed: the config stores paths without a trailing slash; consumers add the separator.

Result 1 — the row count is correct

CheckExpectedActual
Day-1 row count (from Note 03 source interview)574,255574,255 ✔

The file arrived whole. Nothing truncated during upload to the volume — worth confirming before blaming anything downstream.

Result 2 — every column came back as string

root
 |-- step: string (nullable = true)
 |-- type: string (nullable = true)
 |-- amount: string (nullable = true)
 |-- nameOrig: string (nullable = true)
 |-- oldbalanceOrg: string (nullable = true)
 |-- newbalanceOrig: string (nullable = true)
 |-- nameDest: string (nullable = true)
 |-- oldbalanceDest: string (nullable = true)
 |-- newbalanceDest: string (nullable = true)
 |-- isFraud: string (nullable = true)
 |-- isFlaggedFraud: string (nullable = true)

All eleven — including amount, the four balance columns, step and both fraud flags.

Why

A CSV file contains no type information. It is characters and commas, nothing more. header=true only instructs Spark to take column names from row 1 — it says nothing about types. Given no other instruction, Spark takes the only safe option available and calls everything a string. Values that look numeric are still text: how a value looks is not what it is.

Why this is fatal for amount

Text is compared one character at a time, left to right; the first difference decides and length is never considered — dictionary order. "Zebra" beats "Apple" because Z beats A; nobody counts the letters.

Same four valuesSorted as text (what we had)Sorted as number (what we meant)
9.99
85.00
700.00
1000000.00		9.99  ← "max"1000000.00  ← max
85.00700.00
700.0085.00
1000000.009.99

9.99 outranks 1000000.00 because 9 beats 1 at the first character and the comparison ends there.

This is harmless for nameOrig / nameDest — account IDs are genuinely text and no arithmetic is ever done on them. It is ruinous for amount and the balance columns, because nearly every question about money is a size question: biggest transfers, threshold breaches, daily totals, "did this transaction empty the account".

The dangerous part: none of this raises an error. max() and ORDER BY are both perfectly legal on a string column — they simply mean something other than intended. A "top 5 largest transactions" report returns five values beginning with 9, runs green, and looks plausible on a dashboard. A query that runs clean and answers wrong is more dangerous than one that crashes, because nothing tells you to look.

Also why the fraud pattern would vanish

The core signal from Note 03 — "amount equals the entire old balance" — becomes a string equality test. "181.0" and "181.00" are the same number and different strings.

Proving it on our own data

from pyspark.sql import functions as F

df.agg(
    F.max("amount"),                          # lexicographic max
    F.max(F.col("amount").cast("double")),    # true numeric max
).show()

Or in SQL, which puts both answers in one row:

df.createOrReplaceTempView("raw_txn")
SELECT
  max(amount)                 AS text_max,
  max(cast(amount AS double)) AS real_max
FROM raw_txn

Aside: why a temp view was needed at all

QuestionAnswer
Why can't SQL see df?df is a Python variable in the notebook process. A %sql cell goes to Spark's SQL engine, which resolves names against a catalog — it has never heard of a Python variable. createOrReplaceTempView registers a catalog name pointing at the dataframe: the bridge between the two namespaces.
Does it copy data?No. It attaches a name to the dataframe's logical plan — the recipe. Querying the view re-runs the recipe (re-reading the CSV). Free to create, does no work until queried.
Does it belong in the data model?No. Session-scoped, vanishes when the notebook detaches, invisible in Unity Catalog. A scratch alias, not an object. Nothing about it belongs in bronze.
Why not query the file directly with read_files()?It would have hidden the bug. read_files infers the schema by default, so amount would arrive as a double and the experiment would show nothing. The temp view was correct here precisely because it preserves the all-strings dataframe exactly as Spark built it.

The trap that makes it worse: inconsistent coercion

Operation on the string columnWhat Spark doesResult
WHERE amount > 200000String column vs numeric literal — Spark quietly casts the column to doubleCorrect answer
ORDER BY amount DESCNo numeric literal involved — stays a string comparisonWrong answer, silently
max(amount)Lexicographic maximumWrong answer, silently

Some operations coerce, others don't, and the query text gives no clue which. That inconsistency — not any single wrong result — is the real argument for fixing the type once at read time instead of casting defensively at every use site.

Why inferSchema is not the fix

ProblemConsequence
Costs an extra full pass over the dataSpark reads the whole file once to guess, then again to load. Tolerable at 42 MB; not at 42 GB.
The guess depends on the rows it happened to seeSchema drift between batches. Day 1 may infer amount as double; a later day where every value is whole may infer long. Bronze's schema then changes between loads and downstream breaks for reasons unrelated to any code change.

A schema you declare is a contract you enforce. A schema Spark guesses is a coincidence. This is the reasoning behind the bronze contract rule — now confirmed by observation rather than assumed.

How to avoid this in future

#PracticeWhy
1Declare an explicit StructType for every schemaless source (CSV, JSON). Never the default, never inferSchema.Types become a decision on the record, not a by-product of whichever rows arrived.
2Define each schema once in src/ and import it into notebooks and tests alike.One definition can be asserted against; a schema copy-pasted into three notebooks silently diverges.
3Assert the schema in code, don't eyeball it. A pytest check comparing the read schema to the declared contract turns "the source changed its columns" into a red CI run instead of a silent wrong number weeks later.This is the durable fix. Everything else depends on someone remembering to look.
4Make printSchema() the first thing run after any new read — treat it as part of ingestion, not curiosity.Costs seconds; catches the entire class of problem at the only moment it is cheap to fix.
5For any column intended as numeric, sanity-check once with max(col) vs max(cast(col AS double)).A two-second query that distinguishes "typed correctly" from "looks fine, sorts wrong".
6Never read "the query returned rows" as "the query returned the right rows".Type bugs in SQL surface as plausible output, never as errors.
7If using read_files() or COPY INTO later, pass explicit schema hints rather than accepting inference.Convenience functions default to guessing — the same trap wearing a nicer API.

Open question (unresolved)

The bronze schema in Note 03 declares amount as DOUBLE. Double is binary floating point — 0.1 + 0.2 ≠ 0.3 — and financial systems conventionally store money as DECIMAL.

To decide: does bronze keep DOUBLE on the grounds that bronze mirrors the source as-is and PaySim's CSV is float-native, deferring DECIMAL to silver where reshaping is allowed? Or is a money column typed as DOUBLE a defect worth correcting at the boundary? Answer to be recorded here once reasoned through.

You learn: why schemaless formats default to strings, how lexicographic comparison silently corrupts numeric logic, Spark's inconsistent type coercion, the real cost of inferSchema, temp views as the Python↔SQL bridge, and schema assertion as the engineering answer to all of it.

Note 06 — When the Source Changes: Schema Evolution · July 2026

The question

Note 05 settled why bronze declares an explicit schema. The obvious follow-up: what happens months from now when the source file itself changes shape?

The answer that reframes it: an explicit schema does not stop the source from changing — nothing can, the file belongs to someone else. What it provides is a fixed expectation for reality to contradict. With inferSchema there is no expectation at all, so a change quietly becomes the new normal. With a declared schema, a change is a contradiction — and a contradiction can be caught.

A declared schema doesn't stop change. It makes change fail loudly instead of quietly.

Mental model

A StructType is a form with 11 labelled boxes. A CSV row is a line of values. Spark pours the values into the boxes in order — and by default does not read the file's header to check the names. If the source changes shape, the values still land in boxes; they just land in the wrong ones. The form comes out looking perfectly filled in.

Three ways a source can change — behaviour with an explicit schema

The source…Spark does…You get…
Adds a 12th columnReads only the 11 declaredThe new column is thrown away. No error, no warning — arguably the worst case, because everything looks healthy while data is lost.
Swaps / reorders two columnsFills the slots by position; the file's header is ignoredValues land in the wrong columns — correctly typed, entirely plausible, completely wrong. Every downstream number is corrupt and nothing complains.
Sends an unparseable value (amount = "N/A")Can't read it as a number; default PERMISSIVE modeThat value becomes null. No error. Indistinguishable from a genuine null.

The pattern in all three: Spark finishes happily and hands back a wrong answer.

Important — these are the explicit schema failure modes

Easy to misread these as arguments for inferSchema. They are not. They are the reason an explicit schema needs one additional option alongside it.

Honest comparison

Source changeWith inferSchemaWith explicit schema
Adds a columnPicked up automatically — but the bronze table's shape changes without anyone decidingDropped silently
Swaps two columnsHandled correctly — it reads the header for namesValues land in the wrong boxes
Sends "N/A" in amountThe whole column reverts to text — the Note 05 bug returns, triggered by a single bad rowThat one value becomes null

inferSchema genuinely wins the middle row — worth stating plainly rather than pretending otherwise. But the cost is that the source is in charge of your types: the table restructures itself on row 1, and a single bad value among 574,255 rows silently breaks every calculation on row 3.

The fix

df = (
    spark.read
    .format("csv")
    .option("header", "true")
    .option("enforceSchema", "false")   <-- added
    .schema(transactions_schema)
    .load(source_file)
)
PieceWhat it buys
.schema(...)Types are a decision on the record, not a guess that can drift between batches.
enforceSchema = falseCloses the one gap where inference was ahead. Spark validates the file's header names against the declared schema and fails on mismatch, converting silent column-swap corruption into an immediate, obvious error.

Neither piece is sufficient alone: fixed types and a loud failure when the source moves.

When a change turns out to be real

Kind of changeHow bronze absorbs it
Additive (new column)Add the field to the StructType and write with Delta mergeSchema. Historic rows carry null for the new column — which is honest: those rows genuinely never had that field.
Type changeThe painful case. Requires a deliberate rebuild rather than an in-place edit — which is precisely why bronze stores the source untouched. Rebuilding downstream from an unmodified bronze is always possible; recovering data bronze never captured is not.

Because bronze is append-only and stores raw source data, no schema change is ever a dead end.

Forward link — Auto Loader (Phase 3)

Auto Loader automates exactly this: schemaEvolutionMode decides what happens when new columns appear, and rescuedDataColumn captures anything unexpected instead of discarding it — directly fixing failure #1 above. Meeting these three failures by hand first is what makes Auto Loader legible later rather than magic.

Vocabulary clarified

TermMeaning
CoercionSpark silently converting a type on your behalf — e.g. seeing amount > 200000, noticing a string against a number, and casting the column to double without asking or warning. The Note 05 trap.
CoalesceUnrelated, and confusingly two different things: coalesce(a, b, c) in SQL returns the first non-null value from a list; df.coalesce(n) in Python reduces the number of partitions. Same word, no relationship to coercion.

You learn: that schema enforcement is positional by default, the three silent failure modes of a declared schema, the real trade-off against inference, enforceSchema as the missing guard, Delta mergeSchema for additive evolution, and why append-only raw bronze makes every schema change recoverable.

Note 07 — Correction: Bronze Stores Text, Not Types · July 2026

What changed

Bronze now reads every column as STRING. The typed bronze schema from Note 03 (DOUBLE for money, INT for flags) is superseded.

One line to remember: bronze keeps, silver converts.

Why — the contradiction in our own contract

The bronze contract says "no fixes, no filters, no renames." Casting "9839.64" into a double is a fix. The typed schema table sat three lines below the rule that forbade it.

The concrete failure

StepWhat happens
A row arrives with amount = "N/A"Source sends something unexpected — normal in production.
Bronze schema says DoubleTypeSpark tries to parse it as a number and fails.
Default PERMISSIVE modeWrites null. No error, no warning.
The original text is goneIt was never stored. Bronze cannot be replayed to find out what the source actually sent.

Note 03 calls bronze "the time machine — rebuild silver from untouched bronze if the cleaning logic has a bug in month 3." A bronze that silently nulls unparseable values is not a time machine. It has already made an irreversible decision at the door.

What the vendor guidance actually says

Databricks recommends minimal validation in bronze, and — to protect against dropped data — storing most fields as STRING, VARIANT, or BINARY. Schema enforcement belongs to silver.

Precision matters here. The objection is not to declaring a schema in bronze. It is to casting to strict types at read time. Declaring names and column order explicitly is still correct and still recommended; inferSchema is still wrong. Only the types changed.

The three "store it as-is" types

TypeWhat gets storedUse for
STRING ← oursThe characters exactly as they arrived: "9839.64"Flat files — CSV, TSV, plain text
VARIANTNested data with its structure intact — id and tags stay readable later without ever having been declared. Storing raw JSON as a string would work but forces a re-parse on every query.JSON, API responses, event payloads (relevant in Phase 2)
BINARYThe exact bytes. Nothing is read or interpreted at all.Images, PDFs, undecoded formats (not used in this project)

All three do the same job — store it now, understand it later. They differ only in how complicated the stored thing is.

Revised bronze schema — workspace.bronze.transactions

from pyspark.sql.types import StructType, StructField, StringType

transactions_schema = StructType([

    StructField("type",           StringType(), True),
    StructField("amount",         StringType(), True),
    StructField("nameOrig",       StringType(), True),
    StructField("oldbalanceOrg",  StringType(), True),

    StructField("nameDest",       StringType(), True),
    StructField("oldbalanceDest", StringType(), True),
    StructField("newbalanceDest", StringType(), True),
    StructField("isFraud",        StringType(), True),
    StructField("isFlaggedFraud", StringType(), True),

df = (
    spark.read
    .format("csv")
    .option("header", "true")
    .option("enforceSchema", "false")
    .schema(transactions_schema)
    .load(source_file)

Eleven strings again — but by decision this time, not by Spark's default. Audit columns (source_file, ingest_timestamp, batch_date) are unaffected and still added after the read.

What did not change

DecisionStill correct because…
Explicit schema, never inferSchemaInference costs a second full pass and lets the source silently redefine the table's shape (Note 05).
Column names and order declaredStill the contract. Order is positional; names must match the header exactly, ugly ones included.
enforceSchema = "false"Still the guard that turns a silent column swap into a loud failure (Note 06).
All fields nullableBronze accepts whatever arrives; enforcement is silver's job.

Knock-on effects

ItemResolution
Open question: DOUBLE vs DECIMAL for amount (Note 05)Dissolved at bronze. It becomes a silver decision, made where transformation is permitted.
Note 05's "amount sorts wrong" lessonStill true, and now a known, accepted property of bronze rather than a bug. Nobody runs analytics against bronze. Silver's casting step is what fixes it — and a value that fails to cast becomes a quarantined row with a reason attached, instead of a silent null.
Note 03 bronze schema tableMarked superseded in place; names and order still stand.

The alternative we did not choose

A second legitimate approach keeps typed columns in bronze and adds a rescue mechanism — columnNameOfCorruptRecord for CSV, or Auto Loader's _rescued_data — so unparseable values are captured rather than destroyed. That also preserves replayability.

What is never acceptable is typed bronze with neither — which is exactly what the first draft of this pipeline had. Being able to explain this trade-off is worth more than having picked the fashionable option.

Note 08 — Idempotency: Breaking Append, Choosing replaceWhere · August 2026

The experiment: run the same notebook three times

The rung-1 write was mode("append"). The notebook ran three times (two on Aug 11, one on Aug 12) — each run appended the full day-1 file again. Nothing errored. The table reported June 1 as having 1,722,765 transactions when reality had 574,255. Every downstream number would inherit the 3× lie.

The diagnosis query, and why it worked:

SELECT batch_date, ingest_timestamp, COUNT(*)
FROM workspace.bronze.transactions
GROUP BY batch_date, ingest_timestamp

GROUP BY returns one row per unique combination of the listed columns. One distinct batch_date × three distinct ingest_timestamps = three rows of 574,255 each — the three loads, individually visible. Grouped by batch_date alone it would have shown a single 1.72M row and hidden the evidence. Debugging principle: group by the column that distinguishes the thing you suspect. Suspecting multiple runs → group by the column that differs per run. This is also the audit columns paying rent: without ingest_timestamp, the three loads would be indistinguishable.

Why not UPSERT/MERGE (the course's answer)

ConsiderationFinding for our source
What MERGE is forSources whose rows change: customer addresses, order statuses. Incoming rows carry corrections; match on a key, update matches, insert the rest.
Our source (Note 03 interview)Append-only event data. A transaction never changes after it happens. There is nothing to update, ever.
Our actual diseaseNot "rows arrived with new versions" — "the same file got loaded twice." Different disease, different cure.
The killer: no keyPaySim has no transaction ID. A composite key (nameOrig + step + amount + nameDest) would collide on two legitimate identical payments in the same hour — MERGE would silently drop real data. An UPSERT without a trustworthy key quietly destroys data — worse than a visible triple-load.

Conclusion: for a file-drop source, the unit of idempotency is the batch, not the row. Row-level MERGE enters later (gold aggregates are genuinely mutable; real sources have real keys). Same toolbox, different shelf.

The fix: scoped overwrite

(bronze_df.write
    .format("delta")
    .mode("overwrite")
    .option("replaceWhere", f"batch_date='{batch_date}'")
    .saveAsTable(table_name))
QuestionAnswer
What does replaceWhere do?One atomic transaction: delete every existing row matching the predicate, insert the incoming rows. Scope: only batch_date='2026-06-01'. Other days untouched.
How did one run clean up 1.72M rows?All three loads carried the same batch_date — so all 1,722,765 rows matched the predicate, were removed, and were replaced by one fresh 574,255. The mess and the fix used the same mechanism.
Why overwrite and not append?append's contract is "add rows, touch nothing existing" — the opposite of replacement. replaceWhere is replacement semantics, so it belongs to the overwrite family: "the final state of this scope IS the incoming data." The two named together read oddly but mean: overwrite, limited to the predicate.
Does Delta physically delete rows?No — Delta never edits files in place. The transaction log marks the old Parquet files as removed and adds new ones. Old versions remain reachable (DESCRIBE HISTORY, time travel) until VACUUM. "Delete" is a bookkeeping entry, which is what makes the whole operation atomic.

Proof of idempotency

Three consecutive runs of the fixed notebook → the diagnosis query returns one row: 574,255, single ingest_timestamp (the latest run's). Rerun-count no longer affects final state — the definition of idempotent.

Trade-off recorded

replaceWhere reruns rewrite the batch (new ingest_timestamp, new files). The alternative — a processed-files log in ops that skips known files — never rewrites but needs an extra table and check. Chosen: replaceWhere for simplicity; the ops log arrives later for observability, not dedup. Rung 3 (COPY INTO) automates file tracking; rung 4 (Auto Loader) adds checkpoints — both are this same idea with more machinery.

You learn: idempotency as the core ingestion property, GROUP BY as a debugging instrument, why event data doesn't get UPSERTed and keyless MERGE is dangerous, replaceWhere's atomic delete-and-insert semantics, and Delta's transaction log making "delete" a metadata operation.

Note 09 — Profiling Results & What Fraud Actually Means · August 2026

Seven queries run against 1,068,592 bronze rows (batches 2026-06-01 → 06-05). Method: predict first, then query — a surprise only counts if you committed to an expectation.

The eight findings

#FindingConsequence
1The legacy rule is a total failure. isFlaggedFraud = 0 on all 1,068,592 rows. It flagged 0 of 1,404 frauds.The project's business case. Note: this is a rule engine ("flag transfers > 200,000"), not a model. No transaction in 5 days was large enough to trip it. Rules are brittle — fraudsters simply stay under the threshold.
2Fraud is rare: 1,404 / 1,068,592 = 0.131%Severe class imbalance. Accuracy becomes a garbage metric — "never fraud" scores 99.87%. Phase 5 needs precision/recall, and the full 31 days, because 1,404 positives is thin for training.
3Fraud occurs in exactly two types: TRANSFER (695, 0.785%) and CASH_OUT (709, 0.188%). PAYMENT / CASH_IN / DEBIT: zero across a million rows.Recorded as an observation on a sample, not a hardcoded rule — re-verify on all 31 days. True for PaySim (the simulator only generates fraud this way); would be false in real data, where card, ATM and payment fraud all exist. A limitation of synthetic data.
4The mule pairing is visible in the totals: 695 TRANSFER frauds vs 709 CASH_OUT frauds — nearly 1:1.Evidence for transfer-then-cash-out pairs. Proving it row-by-row is the strongest planned gold feature.
5Drain-to-zero is a powerful signal: 97.8% of fraud rows (1,373/1,404) vs 22.8% of normal rows (243,373/1,067,188) — 4.3× lift.A feature, not a rule. 243,373 legitimate rows also drain to zero, so it shifts a probability rather than deciding a verdict. This distinction is the whole difference between the failed rule engine and a model.
6Balances mostly don't reconcile: TRANSFER 94.7%, CASH_OUT 88.6%, PAYMENT 50.7%, DEBIT 30.6% fail before − amount = after.A property of the source, not a pipeline bug. Flag, never quarantine — quarantining 94% of TRANSFERs would destroy the dataset.
7Zero is a sentinel for "balance unknown," not an actual zero balance.A magic value masquerading as data — the most dangerous dirt, because it is silently valid. Needs its own boolean column in silver.
8Structurally clean: exactly 5 types, no nulls, no non-positive amounts.Cheap expectations that should never fire. If one ever does, something upstream changed.

The meta-lesson: a check that fails everything is a broken check

The reconciliation query reported 230,168 of 230,168 CASH_IN rows broken — 100%. A 100% failure rate is never a data problem.

The rule was wrong: CASH_IN is money coming in, so before + amount = after. The query subtracted. Junior instinct: "the data is terrible, file a bug." Senior instinct: "100% is suspicious — re-read my own rule first."

The mirror image is equally true: if a check passes 100% of the time, verify it is capable of failing at all.

SQL patterns learned (worth keeping)

PatternWhy it works / why it matters
SUM(CAST(flag AS INT)) counts a 0/1 columnEach 0 adds nothing, each 1 adds exactly one — the sum is the count. Does not work for 'Y'/'N': CAST('Y' AS INT) returns null, SUM skips nulls, and you get 0 frauds with no error. Use SUM(CASE WHEN flag='Y' THEN 1 ELSE 0 END).
100.0 *, never 100 *Integer ÷ integer truncates. 70900/377263 = 0.188 → 0. Every percentage prints as 0.000 and nothing warns you. Rule: when dividing two counts, force one side to decimal.
SUM(CASE WHEN … THEN 1 ELSE 0 END) vs WHEREWHERE deletes rows; CASE WHEN labels them. After WHERE removes the good rows you have no denominator — "334,368 broken" out of what? CASE WHEN keeps every row, so COUNT(*) and SUM(...) both survive and you get a rate, per group, in one pass. (COUNT(CASE WHEN … THEN 1 END) does the same via nulls.)
ABS(diff) > 0.01, never <> 0DOUBLE stores decimals in binary; most have no exact form, so arithmetic leaves dust (0.0000000000002 instead of 0). Exact-equality would flag balanced rows as broken. 0.01 = one cent; smaller is noise. Never test floats for exact equality. Also why banks store money as DECIMAL.
GROUP BY returns only combinations that existTwo 0/1 columns could yield 4 rows; we got 2, because isFlaggedFraud=1 never occurs. You will never see COUNT(*) = 0 in a GROUP BY result. Absent categories vanish silently — the fix when you need them is a LEFT JOIN from a reference list. Will matter in gold (a customer with no transactions that day).
COUNT(*) − COUNT(col) = null countCOUNT(*) counts rows; COUNT(col) counts non-null values. Does not catch '' — an empty string is a value, not a null. In CSV, "missing" is a spectrum: null, '', ' ', 'NULL', 'N/A', '-'. Check blanks as well as nulls on text columns.
AND balance_before > 0 in the drain checkWithout it, accounts that were already empty (0 → 0) count as "drained" — nothing was taken because nothing was there. "Drained" requires both halves: there was money, and afterwards there wasn't.

The confusion matrix (learned from query 4)

isFraud and isFlaggedFraud are not two degrees of certainty about the same thing. They are two different actors: isFraud is the truth (what actually happened, known after the fact); isFlaggedFraud is a prediction (what the rule engine guessed at the time).

Rule said "fraud"Rule said "fine"
Actually fraud(1,1) true positive — the goal(1,0) missed it — 1,404 rows
Actually fine(0,1) false alarm — expensive: a real customer blocked at checkout(0,0) correctly ignored — 1,067,188 rows

This is the confusion matrix, how every fraud model on earth is evaluated. Our result: two cells populated, both in the "rule said fine" column. Phase 5 builds one of these for our own model.

What actually counts as fraud?

In PaySim: fraud is defined by provenance, not behaviour — the simulator has fraud agents that take over accounts and drain them, and isFraud=1 means "generated by a fraud agent." Perfect ground truth, which exists nowhere in reality.

In a real bank: fraud is whatever an investigation confirmed. A customer disputes a charge, an analyst reviews, a case closes as confirmed or not. So labels are late (weeks), incomplete (undetected fraud stays labelled 0 forever) and subjective (an analyst decided). A model learns from human judgements, not truth.

Different definitions, even inside one bank

TeamWhat they call fraud
Card fraudStolen card / card-not-present. Victim is usually the bank or merchant.
Account takeoverSomeone else got into your account. Closest to PaySim.
Scams (APP fraud)You made the payment — because a criminal tricked you. Contentious: you authorised it, so is it fraud? UK regulators forced reimbursement; other jurisdictions haven't.
First-party fraudThe customer is the fraudster — takes a loan intending never to repay. Often classified as credit risk, not fraud.
AMLMoney laundering. Separate team, separate regulator, separate systems. The movement may be legitimate; the source is criminal.
Application fraudFake or synthetic identity at signup.

Same bank, six teams, six definitions, six models — and boundary disputes are constant, because budget and blame follow the classification.

Practical rule: never accept a label column without asking who created it, when, and by what process.

You learn: profiling as evidence-gathering, the SQL patterns above (integer division, CASE WHEN vs WHERE, float tolerance, GROUP BY's data-driven groups), confusion matrices, rules vs features, class imbalance, and that "fraud" is an organisational definition rather than a fact.

Note 10 — Silver Design Specification · August 2026

What silver is for

Same rows, made trustworthy and usable. Grain is unchanged — one transaction, one row. Three jobs: cast text to real types, rename to clean names, and add derived columns that answer questions a raw row cannot. Nothing is aggregated; that is gold's job.

Why bother: every fraud question needs those derived columns. Compute them once, correctly, here — or fifty analysts each write their own broken version of "did this drain the account."

Before and after

BRONZE (text, ugly names, no event time, no signal)

SILVER

balance_reconciles    = true

is_fraud              = true

How the column list was derived (the method, not the answer)

RuleApplied here
1. Keep everything from bronzeSilver isn't about dropping columns; it's about making them usable. Drop only what is genuinely meaningless — note isFlaggedFraud survives despite being all zeros, because "useless data" and "evidence the old system failed" are different things.
2. Rename what's wrongoldbalanceOrg/newbalanceOrig are inconsistent and a trap; type is a SQL reserved word. Names are fixed exactly once, here.
3. Cast what gets used numericallyAnything used in arithmetic or comparison. nameOrig stays a string forever — you never add two account IDs.
4a. Derive from profiling findingsBalances don't reconcile → balance_reconciles. Zero means unknown → sender_balance_unknown. The M prefix → is_receiver_merchant.
4b. Derive from consumer questions"Was the account drained?" → sender_emptied. "How much of the balance moved?" → drain_ratio. "When did it happen?" → event_timestamp.

Test for belonging in silver: computable from a single row (aggregates belong in gold) · more than one consumer wants it · easy to get wrong. drain_ratio passes all three — one division, universally needed, and forgetting the divide-by-zero case is a classic bug.

This is why profiling came first: the column list is literally derived from it. Designing silver before profiling would have missed sender_balance_unknown entirely, because we wouldn't have known zero was a lie.
